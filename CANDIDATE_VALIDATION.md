## 2. Root-Cause Merge Analysis

| Candidate | Root Cause                                                                                                                                                                                                                                           | Overlaps                                                                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C1**    | **Intake has no application-layer auth** — `Intake.ts:34` calls `MessageFactory.createMessage()` without origin/sender check. TODO at `Intake.ts:13-14` documents awareness                                                                          | C1 enables C3 (PubSub access → arbitrary `poolAddress`)                                                                                            |
| **C2**    | **No per-key permission scoping + blockchain-fallback balance check reads attacker-supplied on-chain data** — `auth.ts:118` stores `apiKeyId` but never checks downstream. `order.ts:204-243` blockchain fallback trusts vault address on-chain data | C2 enables C3 (API key + fake vault → executor calls fake address). C2 is the only way to publish to PubSub with authentic trading-api credentials |
| **C3**    | **`getContract()` loads trusted ABI from DB but applies at attacker-supplied address** — `ExecutorAbstract.ts:107` uses `specifiedAddress ?? address`, where `specifiedAddress` = `task.data.poolAddress`                                            | C3 is the **mechanism** (not a distinct root cause) — both C1 and C2 use the same executor code path                                               |

**Merge verdict:** C1 and C3 share a dependency chain but have **distinct root causes** (no auth vs. no address validation). They should **NOT be merged**. C3 should be recognized as the _mechanism_ by which C1 and C2 execute against arbitrary addresses, not a standalone vulnerability.

**Candidate 2 depends on Candidate 3** — the fake vault path relies on `getContract()` behavior (C3) to call attacker-supplied address with real ABI.

### Key evidence that changed the assessment from CRITICAL_CANDIDATES.md:

1. **On-chain Merkle proof verification** — `DualTokenVault.sol:239-241` proves `msg.sender` (the executor wallet) is an authorized trader. This means C1's attack IS possible (executor signs, proof passes) but also that the executor wallet has limited capabilities (no vault token ownership).

2. **Executor wallet fund analysis** — executor holds gas ETH only (~0.05-0.15 ETH per wallet per DEPLOYMENT.md config). No vault tokens. This kills C2 and C3 as fund-loss vectors.

3. **`minAmountOut` computation** — in the trading-api flow, `calculateMinAmountOut()` applies 25 bps slippage to the DEX quote. Attacker cannot set `minAmountOut: 1` via the API. This prevents "drain at near-zero output" through C2.

4. **C3 is a mechanism, not a vulnerability** — `poolAddress` override at `ExecutorAbstract.ts:107` is by design for dynamic vault deployment. Without a fund loss path stemming from it, it is an architectural observation.
