**Attack path:**

1. Attacker gains ability to publish to the `EXECUTOR_PUBSUB_TOPIC` (GCP PubSub topic)
2. Attacker crafts a `HodlBondsTradeData` message with:
   - `op: "BLACKHOLE_EXACT_IN"` (or any supported op)
   - `quantity: "999999999999999999999999999999999999"` (all tokens)
   - `minAmountOut: "1"` (bypasses slippage protection — accept nearly zero output)
   - `poolAddress: <0xATTACKER_CONTRACT>` (executor calls attacker's contract)
   - `inputToken: <0xVAULT_STABLE_TOKEN>` (real token address)
   - `deadline: <far future>`
3. Intake GCF receives the message, validates FORMAT (not authorization), inserts `queue` task
4. Executor picks up the task, creates `Contract` with real DualTokenVault ABI **pointed at attacker's address**
5. Executor signs + broadcasts transaction to `poolAddress` with the malicious parameters
6. The executor wallet's HD key signs a real transaction, paying gas, on an attacker-controlled target

**Required attacker capability:**

- Ability to publish messages to the `EXECUTOR_PUBSUB_TOPIC` PubSub topic

**Direct impact:**

- If `poolAddress` is a real vault: executor executes a trade with `minAmountOut: 1`, accepting near-zero output → **direct fund loss** from vault
- If `poolAddress` is a malicious contract with matching 4-byte function selector: executor signs a transaction against the attacker's contract, potentially enabling arbitrary state changes using the executor wallet's authority
- The only field NOT attacker-controlled is `merkleProof` (generated by executor) — all other calldata parameters are from the message

**Why it meets bounty scope:**

- **Category 1: Unauthorized fund transfer** — executor signs real transactions with real HD wallet keys executing attacker-specified parameters
- **Category 7: Race condition duplicating/manipulating fund transfer** — `minAmountOut: 1` removes slippage protection
- **Category 8: Broken auth / IDOR / privilege escalation reaching execution** — intake lacks any application-level auth

**Minimal PoC plan:**

1. Create a GCP PubSub publisher client (authenticated as any principal with `pubsub.topics.publish` on the topic)
2. Publish a `HodlBondsTradeMessage` with `minAmountOut: "1"`, targeting any real vault
3. Observe the executor picks up the task, signs, and broadcasts the transaction
4. Verify transaction on-chain shows the swap executed at near-zero output

**Exact test that must pass before this can become a report:**

- Verify that an appropriately-authenticated PubSub publisher (NOT the trading-api's service account) can successfully push a task to the executor DB through the intake
- If PubSub IAM is locked to only the trading-api SA, this path is blocked at the infrastructure level — **this requires the IAM config check**

## VALID CANDIDATE 2 — Trading-API Publishes to Executor PubSub With Attacker-Controlled `quantity` Bypassing All Meaningful Validation

**Status:** `VALID_CANDIDATE`

**Affected files/functions:**

| File                                         | Lines    | Role                                                                                                    |
| -------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------- |
| `trading-api/src/services/order.ts`          | L169-335 | Full order flow: `size` from user → parsed by `inputToken.parse(size)` → `quantity`                     |
| `trading-api/src/services/dex/blackhole.ts`  | L243-253 | `executeSwap()` publishes `quantity: this.inputToken.parse(this.tradeConfig.size).toString()`           |
| `trading-api/src/services/dex/lfj.ts`        | L218-227 | Same pattern as blackhole                                                                               |
| `trading-api/src/services/dex/uniswap-v4.ts` | L139-151 | Same pattern, plus `simulateSwap` is **not implemented** (L133-137)                                     |
| `trading-api/src/services/order.ts`          | L261-269 | Balance check — uses `inputToken.balance` from **attacker-supplied vaultAddress** (blockchain fallback) |
| `trading-api/src/services/dex/utils.ts`      | L22-27   | `calculateMinAmountOut()` — only 25 bps slippage, no absolute floor                                     |

**Source-level evidence:**

```typescript
// order.ts:261-269 — Balance check reads from user-supplied vaultAddress
const inputToken = side === "buy" ? orderData.stableToken : orderData.vaultToken
const requiredAmount = inputToken.parse(size)
const availableBalance = inputToken.balance
if (!availableBalance || availableBalance < requiredAmount) {
    throw errors.unprocessableEntity(...)
}
```

When the DB fallback path is used (bond not found in DB), the `inputToken.balance` comes from **on-chain data at the user-supplied vaultAddress**. If the attacker deploys a contract that returns arbitrary balances, this check passes trivially.

```typescript
// blackhole.ts:243-253 — quantity = user-controlled size, no bounds checking
const messageId = await executorClient.publishHodlBondsTradeUpdate(
	this.executorNetwork,
	{
		op: HodlBondsTradeOp.BLACKHOLE_EXACT_IN,
		clientOrderId: this.tradeConfig.clientOrderId,
		poolAddress: this.tradeConfig.vaultAddress, // user-controlled
		inputToken: this.inputToken.address(this.tradeConfig.chainId),
		quantity: this.inputToken.parse(this.tradeConfig.size).toString(), // user-controlled size → quantity
		minAmountOut: params.minAmountOut.toString(), // computed from quote
		deadline: Number(params.deadline), // computed
	},
);
```

The `size` field (decimal string from user) is parsed by the token's decimals and converted to a raw integer string. There is NO upper bound on `size` beyond the token's max supply. The balance check is bypassable via the blockchain fallback with an attacker-controlled vault contract.

```typescript
// uniswap-v4.ts:133-137 — No simulation at all
simulateSwap(_params: DexSimulateParams): Promise<void> {
    console.log("Uniswap V4 swap simulation skipped (not implemented)")
    return Promise.resolve()
}
```

Uniswap V4 orders skip simulation entirely — no pre-flight validation at all.

**Attack path (via valid API key):**

1. Attacker has a valid HMAC API key (legitimate user or compromised key)
2. Attacker deploys a contract that implements the `DualTokenVault` interface (`getVaultConfig`, `getVaultData`, `getVaultTokenBalance`, `blackholeSwapExactInputSingle`):
   - Returns fabricated but valid-seeming vault data
   - Returns inflated balances for the balance check
   - The `blackholeSwapExactInputSingle` function on the fake vault can either:
     a. Pass simulation, then the executor calls it with real token amounts — the fake vault accepts the call but no real tokens move (executor wallet doesn't hold vault tokens)
     b. Actually matches the DualTokenVault interface selector, allowing the executor to call it
3. POST `/v0/orders/{chainId}` with:
   - `vaultAddress`: attacker's contract address
   - `side`: "sell"
   - `size`: "9999999999999999" (large amount)
   - `clientOrderId`: some unique 32-hex
4. Balance check passes (fake vault returns inflated balance)
5. DEX quote + simulation pass (fake vault implements compatible functions)
6. Order published to PubSub with attacker-controlled `quantity`
7. Executor picks up task, signs transaction against fake vault
8. Executor wallet pays gas for the transaction.

**More impactful sub-path (Uniswap V4 — no simulation):**
For Uniswap V4 orders, there is NO simulation at all (`uniswap-v4.ts:133-137`). The balance check still runs, but any vault that passes the balance check + quote can have orders published with no pre-flight swap simulation. If the vault is a vault the attacker has deployed that has a `swapExactInputSingle` function (matching the selector), the attacker can set `size` to drain the vault's balance through favorable pricing.

**Required attacker capability:**

- Valid HMAC API key (or ability to publish to PubSub — see CANDIDATE 1)
- Ability to deploy a contract on-chain (costs gas, trivial on testnets, harder on mainnet)

**Direct impact:**

- Category 1: Unauthorized fund transfer through bypassing balance checks via fake vault contracts
- Category 3: Financial fraud causing fund loss — executor signs transactions against attacker-controlled contracts
- Category 8: Broken auth — `apiKeyId` is stored in context (`auth.ts:118`) but **never checked** downstream for authorization

**Why it meets bounty scope:**

- Direct path from API key access → executor signs transactions with attacker-controlled parameters
- No per-key permission scoping — any valid key can place any order on any chain/vault
- Uniswap V4 simulation skip removes the last defense layer for that DEX type

**Minimal PoC plan:**

1. Obtain/deploy a contract on Fuji testnet that implements `getVaultConfig()` returning fabricated data
2. Call POST with the test vault address and a large `size`
3. Verify the order passes validation, gets published, and the executor picks it up
4. For Uniswap V4: demonstrate that orders are published with zero simulation

**Exact test that must pass before this can become a report:**

- Show that an order with `vaultAddress` pointing to a fake vault is accepted and published to PubSub
- Show that the executor creates a transaction targeting the fake vault address

## VALID CANDIDATE 3 — Executor Contract Loading From DB Enables Trusted-ABI Abuse at Attacker-Supplied Address

**Status:** `VALID_CANDIDATE`

**Affected files/functions:**

| File                                                           | Lines   | Role                                                                                                 |
| -------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------- |
| `executor/apps/executor/src/ExecutorAbstract.ts`               | L71-115 | `getContract()` loads ABI + address from DB, then creates `ethers.Contract(useAddress, abi, signer)` |
| `executor/apps/executor/src/ExecutorAbstract.ts`               | L107    | `useAddress = specifiedAddress ?? address` — `specifiedAddress` is `poolAddress` from task data      |
| `executor/apps/executor/src/implementations/HodlBondsTrade.ts` | L88-93  | Passes `hodlBondsTradeData.poolAddress` as `specifiedAddress`                                        |

**Source-level evidence:**

```typescript
// ExecutorAbstract.ts:71-115
async getContract(
    contractName: string,
    network: string,
    signer: Signer,
    specifiedAddress: string | null = null,
): Promise<Contract> {
    const result = await db.select({ abi: schema.contracts.abi, address: schema.contracts.address })
        .from(schema.contracts)
        .where(and(
            eq(schema.contracts.contract_name, contractName),
            eq(schema.contracts.network, network),
        )).limit(1)

    const { abi, address } = result[0]
    const useAddress = specifiedAddress ?? address  // <-- overrides DB address with attacker's

    return new ethers.Contract(useAddress, abi as ethers.InterfaceAbi, signer)
}
```

**Key vulnerability:** The function loads the **trusted ABI** from the database's `contracts` table (the real DualTokenVault ABI) but uses the **attacker-supplied address** (`poolAddress` from task data) as the target contract address. This means the executor:

1. Loads the real DualTokenVault ABI (correct function signatures)
2. Bundles calldata using that ABI encoding
3. Sends the transaction to the attacker-supplied address

If the target contract has a function with the same 4-byte selector as `blackholeSwapExactInputSingle`, `lbSwapExactInputSingle`, or `swapExactInputSingle`, the calldata will execute that function with the attacker's parameters.

**Attack path:**

1. Attacker deploys a contract with function selector matching `blackholeSwapExactInputSingle(uint128,uint128,address,uint256,bytes32[])` (4 bytes), or brute-forces a function with the exact same 4-byte selector
2. The attacker's function can decode the parameters and do arbitrary operations
3. The executor signs and broadcasts the transaction
4. The executor wallet pays gas; the attacker's contract processes the calldata

**Required attacker capability:**

- Ability to publish to PubSub topic (or valid API key + fake vault deployment — see CANDIDATE 2)
- Deploy a contract with matching 4-byte function selector (computationally feasible — ~2^31 attempts expected)

**Direct impact:**

- The executor's HD wallet signs a real transaction against an attacker-controlled contract
- At minimum: gas funds lost (executor wallet pays for failed/successful transactions)
- At maximum: if the attacker's contract can interact with approved DeFi protocols or exploit the executor wallet's authority, fund loss escalates

**Why it meets bounty scope:**

- Category 1: Unauthorized fund transfer — HD wallet keys sign unauthorized transactions
- Category 4: Hot/cold wallet compromise — real signing keys used on attacker-controlled targets

**Minimal PoC plan:**

1. Compute function selector for `blackholeSwapExactInputSingle(uint128,uint128,address,uint256,bytes32[])` = `keccak256("blackholeSwapExactInputSingle(uint128,uint128,address,uint256,bytes32[])")[:4]`
2. Deploy a contract on testnet with a function having the same selector
3. Publish a PubSub message targeting this contract
4. Observe the executor signing and broadcasting the transaction

**Exact test that must pass before this can become a report:**

- Verify the function selector of the DualTokenVault ABI's swap functions
- Demonstrate that the executor's transaction targets the attacker's contract address with the correct calldata encoding

## KILLED CANDIDATES

### KILLED CANDIDATE 4 — Oracle Validation Only on Mainnet

**Status:** `KILL`

**Rationale:** `oracle.ts:97` checks `!client.chain.testnet` before enforcing the 3% deviation limit. On testnets (Fuji, Sepolia), quotes are not validated against Chainlink oracles. However, testnet tokens have no real economic value, and this is by design for development flexibility. No direct critical fund loss path.

### KILLED CANDIDATE 5 — HMAC Cross-Instance Replay

**Status:** `KILL`

**Rationale:** The `auth.ts:54-59` replay cache is per-instance (in-memory LRU). Multiple Cloud Run instances do not share the cache. A replayed request could be accepted by a different instance. However, the DB `onConflictDoNothing` on `clientOrderId` (`order.ts:189`) prevents duplicate order insertion. No fund duplication path.

### KILLED CANDIDATE 6 — Uniswap V4 Simulation Gap Alone

**Status:** `KILL`

**Rationale:** `uniswap-v4.ts:133-137` has `simulateSwap` as a no-op. By itself, this means orders skip pre-flight validation. However, without a demonstrated price manipulation or parameter injection vector, the simulation gap alone does not cause fund loss. It is an amplifier for other exploits (see CANDIDATE 2).

### KILLED CANDIDATE 7 — OIDC Status Callback Abuse

**Status:** `KILL`

**Rationale:** `order-status.ts:16-24` validates OIDC tokens via Google's `verifyIdToken()` with audience + email checks. The terminal state guard (L77) and timestamp ordering (L86) provide defense-in-depth. No code-level bypass identified. Token forgery requires GCP IAM compromise (out of scope per program rules).

### KILLED CANDIDATE 8 — Executor Seed Phrase In-Memory Exposure

**Status:** `KILL`

**Rationale:** `WalletManager.ts:117` sets `seedPhrase = null` after wallet initialization. Derived private keys persist in `Wallet.signer` objects. No code path reads the seed phrase after initialization. This is an architectural observation (no HSM/KMS), not an exploitable code-level vulnerability in the in-scope source.

### KILLED CANDIDATE 9 — Executor uint128 Clamping in Simulation Only

**Status:** `KILL`

**Rationale:** `blackhole.ts:220-221` clamps `amountIn > 2^128-1` to `2^128-1` during **simulation** only. The actual executor call in `HodlBondsTrade.ts:109-148` passes `hodlBondsTradeData.quantity` **unclamped**. If the quantity exceeds uint128, the on-chain call would revert at the contract level (the DualTokenVault contract uses uint128 parameters). This causes execution failure (gas wasted), not fund loss. No overflow/underflow risk since the quantity is a string parsed by the executor.

### KILLED CANDIDATE 10 — task_hash Collision / Dedup Bypass

**Status:** `KILL`

**Rationale:** `Intake.ts:48` uses `computeHash(message)` for dedup. Hash collision is computationally infeasible. The fallback dedup (L79-115) re-queries by all fields including `task_hash`. No practical bypass.

### KILLED CANDIDATE 11 — DB Connection String Injection

**Status:** `KILL`

**Rationale:** `executor/config/index.ts:7` parses `process.env` through `BaseConfigSchema` which validates `DATABASE_URL` format (regex). The intake's `config/index.ts:14-24` reads `DB_USER`, `DB_INSTANCE_ID`, `DB_NAME` from env vars — no user input reaches these values. No injection path.

### KILLED CANDIDATE 12 — HMAC Cross-Instance Replay + API Key Brute Force

**Status:** `KILL`

**Rationale:** `API_KEYS` is a `Map<string, string>` from env vars. UUID-based key IDs prevent brute force. The dummy secret fallback (`auth.ts:89`) prevents timing attacks on key existence. No extraction path for keys from source code.

### KILLED CANDIDATE 13 — Vault Balance Check Using On-Chain Data (Blockchain Fallback)

**Status:** `KILL` (subsumed into CANDIDATE 2)

**Rationale:** The blockchain fallback in `order.ts:204-243` reads vault data from on-chain at the user-supplied `vaultAddress`. An attacker-deployed contract can return fabricated balances. This is an amplifier for CANDIDATE 2, not a standalone critical issue. Without a fake vault that also passes simulation, the balance check bypass alone cannot reach execution.
